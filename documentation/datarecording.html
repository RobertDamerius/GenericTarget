Data Recording

Data recording is performed with the Write Bus To File block. Recorded data is written to files automatically: each sample is first written into an internal ring buffer, and a dedicated non-realtime recording thread transfers the buffered samples to the data files. Every data recorder object is identified by a unique ID, which is also used in the names of the recording files.

Initialization

During initialization of the Simulink model, a new data directory is created whose name encodes the start time in UTC with millisecond precision, e.g., 20261119_123456789. All recording IDs are checked for validity and uniqueness: an ID must be non-empty, at most 64 characters long, contain only alphanumeric or underscore characters, and occur only once within the model. If any of these conditions is violated, initialization of the target application fails. The first data file of each recorder is created during this phase as well.

Termination

During the termination phase, any samples that are still buffered are flushed to the data files, so that no recorded data is lost.

Separate Data Recording Thread

The dedicated non-realtime recording thread of each data recorder object is responsible for writing the buffered samples to the data files in their original order. When the number of written samples reaches the numSamplesPerFile parameter set in the mask of the corresponding Write Bus To File block, the thread automatically opens a new data file and continues writing there; if this parameter is zero, all samples are written to a single file. Every sample is written and synced to physical storage before the next one is touched, so after a crash or power loss only samples that were still in the ring buffer or in the process of being written are lost. If the recording thread cannot keep up with the sample rate, new samples overwrite the oldest ones in the ring buffer and data may be lost (see Ring Buffer).

File Format

Separate data files are created for each recording ID. For an ID of myData, the first data file is named myData_0. When the number of written samples reaches the numSamplesPerFile parameter, a new data file myData_1 is created and subsequent files are named myData_2, myData_3 and so on. If this parameter is zero, no file rotation takes place and a single data file is written, e.g., myData_0. Existing data files are never overwritten or appended to: if a file name already exists, the creation of the file fails.

Every data file has the following structure: 

<json_header> <null byte> <sample 1> <sample 2> ... <sample N>

The JSON header is a string that describes the recorded bus and the size of one sample. It is identical in every file of one recording, so each file can be decoded independently of the other files. A single NUL byte (0x00) terminates the header; all recorded samples follow back to back without separators.

The Header

The header is a JSON object with the following fields:

FieldData TypeDescription
versionstringThe version of the Generic Target framework that wrote the file, e.g., "2.2.0".
numBytesPerSampleuint32Total size in bytes of one sample, including the 28-byte UTC time point.
labelsstringThe signal names separated by commas, e.g., "value,nestedBus.value".
dimensionsstringThe dimensions of all signals separated by commas. A scalar followed by a 3-by-1 vector would be "[1],[3 1]".
dataTypesstringThe data types of all signals separated by commas, e.g., "double,int32".

The header is written and synced to physical storage right after the file has been created, before the first sample. A file without a NUL byte is incomplete: the process crashed while writing the header.

The Samples

Each sample consists of exactly numBytesPerSample bytes: a 28-byte UTC time point followed by the packed binary data of the bus. The seven int32 values of the time point are stored in the native (little-endian) byte order of the 64-bit target, and all samples follow back to back without separators:

Offset (Bytes)Length (Bytes)NameData TypeDescription
04yearint32The year of the UTC time, e.g., 2026.
44monthint32The month of the UTC time [1, 12].
84dayint32The day of the month according to the UTC time [1, 31].
124hourint32The hour of the UTC time [0, 23].
164minuteint32The minute of the UTC time [0, 59].
204secondint32The second of the UTC time [0, 59].
244nanosecondint32The nanoseconds after the second [0, 999999999].
28numBytesPerSample - 28BusDatauint8The packed binary data of the bus: all signals in the order given by labels, each stored as a contiguous byte sequence according to its dimension and data type.

Loading Recorded Data

Recorded files can be loaded into MATLAB with the GT.LoadDataFiles() function, which deserializes them into a structure of time tables with nanosecond-precision timestamps. The GT.LoadDataDirectory() function loads all recordings from a data directory automatically. Incomplete trailing samples in a file, e.g., after a crash or power loss, are ignored with a warning.
