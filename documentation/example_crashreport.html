Analyzing Crash Reports

If the target application crashes, a backtrace is written to the console output. The backtrace identifies the location in the code that caused the crash. To get meaningful results, it is strongly recommended to compile the application with DEBUG mode enabled: optimizations are disabled and the symbol table is retained in the executable. The binary is slightly larger and task execution may be a bit slower. In some cases, DEBUG mode can also reveal task overloads or CPU overloads that might otherwise remain hidden when all optimizations are enabled.

DEBUG mode can be enabled in two ways: redeploy the application with the compiler flag additionalCompilerFlags.DEBUG_MODE, or modify the Makefile on the target and recompile manually — the latter is especially useful if code generation takes a long time.

Variant 1: Set DEBUG Mode before Deployment

To enable DEBUG mode during deployment, set the flag on the target object before calling the Deploy method: 

target = GT.GenericTarget(username, address);
target.additionalCompilerFlags.DEBUG_MODE = true;
target.Deploy(modelName);

Variant 2: Modify DEBUG Mode and Recompile Manually

Navigate to the application directory on the target and open the Makefile. Near the beginning, find the line that starts with DEBUG_MODE := and set it to: 

DEBUG_MODE := 1

Save the Makefile and open a terminal in the same directory. Rebuild the application from scratch by clearing the build cache and compiling with 8 parallel jobs: 

make clean && make -j8

The compilation is successful if the last message reads [APP] > GenericTarget and no errors were reported.

Viewing the Output

A crash report is printed to the console output and looks like this:

==========================================================================
CRASH DETECTED: SIGSEGV (Segmentation fault)
==========================================================================

./GenericTarget(+0x4b2ec) [0x5573dd31b2ec]
/lib/x86_64-linux-gnu/libc.so.6(+0x3fd70) [0x7fa66b595d70]
./GenericTarget(+0x6debf) [0x5573dd33debf]
./GenericTarget(+0x51950) [0x5573dd321950]
./GenericTarget(+0x4ecbb) [0x5573dd31ecbb]
./GenericTarget(+0x5030c) [0x5573dd32030c]
./GenericTarget(+0x50277) [0x5573dd320277]
./GenericTarget(+0x501e7) [0x5573dd3201e7]
./GenericTarget(+0x501a0) [0x5573dd3201a0]
./GenericTarget(+0x50184) [0x5573dd320184]
/lib/x86_64-linux-gnu/libstdc++.so.6(+0xe1224) [0x7fa66b948224]
/lib/x86_64-linux-gnu/libc.so.6(+0x928bb) [0x7fa66b5e88bb]
/lib/x86_64-linux-gnu/libc.so.6(+0x110538) [0x7fa66b666538]

==========================================================================

The report shows the signal that caused the crash (here: SIGSEGV, a segmentation fault) and the backtrace from the most recent call to the oldest. To map a printed address to a source file and line, run the following command in the application directory: 

addr2line -e ./PRODUCT_NAME +0xABCDEF

Here, 0xABCDEF is the printed address offset and PRODUCT_NAME the name of the executable (default: GenericTarget).

Start at the top of the trace and work downward, skipping frames in system libraries. In the example above, addr2line -e ./GenericTarget +0x6debf returns: 

/home/target/GenericTarget/code/SimulinkCodeGeneration/test/model_ert_rtw/model.cpp:196

This identifies the file and line where the crash occurred.

Alternatively, debug the application using VSCode.
