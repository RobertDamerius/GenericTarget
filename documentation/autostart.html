Autostart Target Application

This page describes how to configure the target application so that it starts automatically every time the computer boots, without manual intervention. The configuration is a systemd service file, which also defines where the console output of the application is recorded.

Before proceeding, make sure the application has already been deployed to the target (see Deployment). All commands on this page are executed in a terminal on the target computer. The steps are outlined below.

  • Step 1: Create the systemd service file
  • Step 2: Enable and start the service
  • Verifying the setup

Step 1: Create the systemd Service File

On Linux, systemd is the system manager that starts and supervises programs. A service file in /etc/systemd/system/ describes how a program should be started; once enabled, the corresponding service runs automatically at every boot. Create the service file with: 

sudo nano /etc/systemd/system/generictarget.service

Paste the following configuration into the file:

[Unit]
Description=GenericTarget
After=network.target remote-fs.target

[Service]
Type=simple
User=root

# Optional: Add a brief startup delay if the boot storm causes overloads
ExecStartPre=/bin/sleep 5

# Ensure log file exists and is owned by your regular user before starting
ExecStartPre=/bin/touch /home/UserName/PathToApplication/output.log
ExecStartPre=/bin/chown UserName:UserName /home/UserName/PathToApplication/output.log

# Run application
ExecStart=/usr/bin/taskset 0x0f /home/UserName/PathToApplication/ApplicationName

# Systemd native logging (append mode)
StandardOutput=append:/home/UserName/PathToApplication/output.log
StandardError=inherit

# Restart behavior in case of crashes
Restart=no

[Install]
WantedBy=multi-user.target

Before saving, replace the placeholders with your own values:

  • UserName — the user name on the target computer.
  • PathToApplication — the path of the application directory in the user's home folder (default: GenericTarget).
  • ApplicationName — the name of the deployed executable as found in the application directory (default: GenericTarget).

What the configuration does

The individual directives, in the order they appear in the file:

  • Description=GenericTarget — human-readable name of the service, as shown by systemd status commands.
  • After=network.target remote-fs.target — start only after the network and all file systems are available, so that no part of the system is still initializing when the application starts.
  • Type=simple — standard service type: systemd considers the service started as soon as the ExecStart command has been executed; the process does not fork into the background itself.
  • User=root — run the application with root privileges, matching the manual startup (which is performed via sudo).
  • ExecStartPre=/bin/sleep 5 — optional brief delay before startup. During boot, many services start simultaneously; this burst of activity can cause CPU load spikes and timing overloads in the real-time application. A few seconds of delay lets the system settle first. Remove or adjust this line if it is not needed.
  • ExecStartPre=/bin/touch .../output.log — create the log file in advance so that it exists before the application starts.
  • ExecStartPre=/bin/chown UserName:UserName .../output.log — set ownership of the log file to your regular user, making it readable and writable from a non-root session (for example when reading logs over SSH).
  • ExecStart=/usr/bin/taskset 0x0f ... — start the application pinned to specific CPU cores. The bitmask 0x0f selects cores 0–3; adjust the mask according to the number of available or dedicated cores, or remove taskset entirely if no pinning is required.
  • StandardOutput=append:.../output.log — append all console output to the log file instead of writing it to a terminal (see Console Output).
  • StandardError=inherit — route error output to the same destination as standard output, i.e., also into output.log.
  • Restart=no — systemd does not restart the application if it terminates or crashes.
  • WantedBy=multi-user.target — start the service during normal multi-user boot, i.e., when the system has reached the state in which users can log in.

Important — Crash behavior

With Restart=no, systemd does not restart the application after a crash. The console output — including the crash report — is still written to output.log; see Analyzing Crash Reports. If you want the service to restart automatically, set Restart=on-failure.

Tip — CPU core pinning

The bitmask of taskset selects the cores on which the application runs: bit 0 is core 0, bit 1 is core 1, and so on. For example, 0x0f pins to cores 0–3. Choose a mask that matches the cores available (or dedicated) on your target; for isolating cores from the operating system scheduler, see Isolating CPU cores.

Step 2: Enable and Start the Service

After saving the file, reload systemd so that it recognizes the new service, enable it for automatic startup at boot, and start it immediately: 

sudo systemctl daemon-reload
sudo systemctl enable generictarget.service
sudo systemctl start generictarget.service
  • daemon-reload — makes systemd re-read the unit files so that the new service is recognized.
  • enable — registers the service with multi-user.target, so it starts automatically at every boot.
  • start — starts the service immediately, without rebooting the computer.

Verifying the Setup

Check that the service is running:

systemctl status generictarget.service

The output should show active (running). The console output of the application is appended to output.log; display the most recent lines with: 

tail -n 20 /home/UserName/PathToApplication/output.log

To confirm that autostart works, reboot the target and check the service status again after boot.
