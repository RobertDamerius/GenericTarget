Analyzing Crash Reports

If the target application crashes, a backtrace is written to the console output. This backtrace helps identify the location in the code that caused the crash. It is highly recommended to compile the application with DEBUG mode enabled. In DEBUG mode, all optimizations are disabled and the symbol table is kept in the executable. The resulting binary is slightly larger and task execution may be a bit slower. In some cases, DEBUG mode can also reveal task overloads or CPU overloads that might otherwise remain hidden when all optimizations are enabled. There are two ways to enable DEBUG mode. You can either redeploy the target application with the additional compiler flag additionalCompilerFlags.DEBUG_MODE, or you can modify the Makefile and recompile the application manually. The second option is especially useful if code generation takes a long time.

Variant 1: Set DEBUG mode before deployment

To enable DEBUG mode during deployment, set the appropriate property of the target object before calling the Deploy member function. 
target = GT.GenericTarget(userName, address);
target.additionalCompilerFlags.DEBUG_MODE = true;
target.Deploy(modelName);

Variant 2: Modify DEBUG mode and recompile manually

Navigate to the application directory on the target and open the Makefile. Look for the line near the beginning that starts with DEBUG_MODE :=. Enable DEBUG mode by setting it to 
DEBUG_MODE := 1
Save the Makefile and open a terminal in the same directory as the Makefile. Rebuild the application from scratch by clearing the cache files and compiling with 8 jobs in parallel: 
make clean && make -j8
The compilation was successful if the last message looks like [APP] > GenericTarget and no errors are reported.

Viewing the Output

The crash report is printed to the console output and may look like this: 
==========================================================================
CRASH DETECTED: SIGSEGV (Segmentation fault)
==========================================================================

./GenericTarget(+0x4b2ec) [0x5573dd31b2ec]
/lib/x86_64-linux-gnu/libc.so.6(+0x3fd70) [0x7fa66b595d70]
./GenericTarget(+0x6debf) [0x5573dd33debf]
./GenericTarget(+0x51950) [0x5573dd321950]
./GenericTarget(+0x4ecbb) [0x5573dd31ecbb]
./GenericTarget(+0x5030c) [0x5573dd32030c]
./GenericTarget(+0x50277) [0x5573dd320277]
./GenericTarget(+0x501e7) [0x5573dd3201e7]
./GenericTarget(+0x501a0) [0x5573dd3201a0]
./GenericTarget(+0x50184) [0x5573dd320184]
/lib/x86_64-linux-gnu/libstdc++.so.6(+0xe1224) [0x7fa66b948224]
/lib/x86_64-linux-gnu/libc.so.6(+0x928bb) [0x7fa66b5e88bb]
/lib/x86_64-linux-gnu/libc.so.6(+0x110538) [0x7fa66b666538]

==========================================================================
This report indicates a segmentation fault and prints the backtrace from the most recent call to the least recent call. To map a printed address to a source line, run the following command in the application directory: 
addr2line -e ./PRODUCT_NAME +0xABCDEF
Here, 0xABCDEF is the printed address and PRODUCT_NAME is the name of the executable (default: GenericTarget). Start searching from the top of the trace downward. In the above example, the command addr2line -e ./GenericTarget +0x6debf returned the following result: 
/home/target/GenericTarget/code/SimulinkCodeGeneration/test/model_ert_rtw/model.cpp:196
This identifies the file and line number that caused the crash. Alternatively, debug the application using VSCode.
